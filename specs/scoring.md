# Scoring and progress events — sz-rules-1

Status: **accepted delegated implementation decision**, 5 November 2026. PRD v2.2 §3.5 specifies lexicographic score and actions from the final program; the concrete normalization and achievement event boundaries below close T002.

## Successful score

For verified success at integer tick `c`, trim SHIFT after `c` as defined in [identity-and-versioning.md](identity-and-versioning.md). Let `n` be the number of SHIFT ticks in that final list:

```text
score = (n, c, n)
         shift_count, completion_ticks, programming_actions
```

Only one action kind exists, so programming actions currently equals SHIFT count. This makes the third component redundant in baseline gameplay, deliberately; there is no invented click penalty or second command to force it to differ. Preserve all three components for the PRD/API/contract interface. All components are nonnegative integers within the limits; completion ticks are 1..64. Failed/invalid/cancelled runs have no successful score.

Compare tuples left to right: first unequal component decides, lower is better. Equal tuples are tied regardless of wallet, number of attempts, wall clock, submission time, hints outside competition, animation speed, undo count or editing history. Never compare a string representation or weighted scalar. Competitive rank is `1 + count(wallets with a strictly better best verified tuple)`: ties produce `1,1,3`, not dense ranking and not timestamp ordering.

The generic tuple comparator still compares all three components, including hand-authored interface fixtures whose third field differs. A score generated by the baseline verifier must additionally satisfy `programming_actions == shift_count`; a tuple inconsistent with this is rejected, not trusted because it sorts correctly.

## Attempts and completion event

- Attempts are per local profile + puzzle hash + rules/engine version, persisted offline. A new attempt starts once when the player first advances tick 1 for an editable program using Play or Step. Pause/resume and additional Step do not create more attempts.
- Reset/end/stop then starting another forward simulation creates a new attempt, even if the program is unchanged. Editing an attempted program starts no attempt until the next actual tick 1 run. Viewing a saved local/other-player replay, running the solver, previewing a hint, loading a board, or undoing an edit never counts.
- On an attempt's first successful terminal event, save completion and best score atomically. Replayed/delivered-twice terminal events use attempt IDs to avoid duplicate progress/achievement changes.
- “After ten attempts” for **Never Give Up** means success on attempt **10 or later**, with the current successful attempt included: attempts 9/10/11 yield locked/unlocked/unlocked. The first nine may be failures or voluntary restarted attempts that reached tick 1. This closes an ambiguous PRD phrase without secretly requiring ten failures plus an eleventh run.

## Local achievement evidence

| Achievement | Exact evidence |
|---|---|
| First Signal | First successful non-replay puzzle completion. |
| Think Ahead | Complete a puzzle whose minimum feasible SHIFT count is **proven ≥3** under the same rules/tick limit. Three shifts in the player's inefficient program is insufficient. |
| Perfect Timing | Complete in the **global minimum completion ticks over all valid programs**, independent of SHIFT count. That tick optimum must be proven; it is not merely the completion tick of the lexicographically best SHIFT-first solution. |
| Never Give Up | Completion on local attempt 10 or later under the boundary above. |
| Architect | First user-created draft saved as a structurally valid puzzle specification; merely opening Create or importing another person's puzzle is insufficient. Solver validation is not required to acknowledge creating a draft. |
| Signal Creator | First successful Share Code export of a structurally valid user-created draft; opening/cancelling export or importing a code is insufficient. |

Solver output must record objective, result status, proof/budget completion, puzzle hash and versions. A timeout with one solution is not an optimum proof. Think Ahead can be proven by exhaustive rejection of all programs with fewer than three SHIFT plus a valid completion, even if the full best tuple is unknown. Perfect Timing needs a separate tick-first bound/search proof if the default solver objective is lexicographic. No unlock based on unknown or stale metadata after editing the puzzle.

On-chain achievement eligibility remains separate and uses finalized competitive evidence under T006/T081. A Daily streak consists of seven consecutive UTC daily IDs with a verified official completion for the same wallet; a skipped day breaks the streak. Shared daily rank #1 counts as a win; weekly rank ties share qualification. Imported/local backup data never proves on-chain eligibility.

## Examples and review

- `(1,20,1)` beats `(2,2,2)`; fewer SHIFT wins even when slower.
- `(2,5,2)` beats `(2,6,2)`; completion tick breaks an equal SHIFT count.
- Two different edit histories ending in SHIFT `[2]` and success tick 2 both score `(1,2,1)`.
- Submitted `[2,4]`, success tick 2: final program `[2]`, score `(1,2,1)`, and commitment for `[2]`. A SHIFT at tick 65 when limit is 64 is invalid input, not a post-success action to ignore.

Machine-readable cases and manually reviewed tick traces are under `specs/test-vectors/`. There is no production engine/solver yet in this phase; this is the contract those later tasks must satisfy.
